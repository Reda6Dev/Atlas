# AI HANDOFF — موجه تسليم الذكاء الاصطناعي لمشروع Atlas (Atlas AI Handoff Prompt)

أنت الآن تستلم مشروع Android قائم اسمه **Atlas**.
المشروع ليس مشروعًا جديدًا، ولا تبدأ بإعادة بنائه أو إعادة تصميمه من الصفر.

مهمتك أولًا هي **فهم الحالة الفعلية الحالية للمشروع**، ثم متابعة العمل من النقطة التي توقف عندها المشروع، مع المحافظة على التعديلات والقرارات الموجودة.

---

## 1. قاعدة أساسية جدًا (Core Rule)

**لا تفترض أن هذه الرسالة تحتوي على أحدث حالة للمشروع.**

المصدر الحقيقي للحالة الحالية، بالترتيب:

1. ملفات المشروع الكودية الفعلية.
2. سجل Git والالتزام البرمجي الحالي (Commit) والفرع الحالي (Branch).
3. `PROJECT_MAP.md`.
4. `AI_HANDOFF.md`.
5. `ATLAS_CHANGELOG.md`.
6. `توثيق_Atlas/واجهة_المستخدم/` (مرجع واجهة المستخدم).
7. هذه الرسالة.

إذا وجدت تعارضًا بين أي وصف هنا وبين الكود الفعلي أو Git، **لا تفترض أن الوصف صحيح**.

تحقق من الحالة الفعلية أولًا، وسجّل التعارض بدل إجراء تعديل مبني على افتراض.

---

# 2. قبل أي تعديل — ممنوع التعديل مباشرة

قبل إنشاء أو تعديل أو حذف أي ملف:

### اقرأ أولًا:

```text
PROJECT_MAP.md
AI_HANDOFF.md
ATLAS_CHANGELOG.md
توثيق_Atlas/واجهة_المستخدم/ (عند العمل على UI/UX)
```

إذا كان أحد الملفات غير موجود:

* لا تنشئه من نفسك أثناء تنفيذ مهمة أخرى.
* أخبر المستخدم أن الملف غير موجود.
* إذا كانت المهمة الحالية هي إنشاء/إعادة بناء الخريطة أو ملف التسليم، يمكن عندها إنشاؤه وفق التعليمات.

بعد ذلك افحص Git.

---

# 3. تحقق من Git (Check Git Status)

نفّذ أولًا أوامر قراءة فقط مثل:

```powershell
git status --short
git branch --show-current
git log -1 --oneline
git remote -v
```

ثم عند الحاجة:

```powershell
git --no-pager diff
```

ولفهم تاريخ التعديلات:

```powershell
git --no-pager log --oneline --decorate -20
```

إذا كانت هناك تعديلات غير محفوظة في Git:

```text
M
A
D
??
```

فلا تحذفها ولا تستبدلها ولا تعمل reset عليها من نفسك.

هذه التعديلات قد تكون جزءًا من عمل المستخدم.

---

# 4. ممنوع استخدام أوامر Git خطرة بدون موافقة صريحة

لا تستخدم من نفسك:

```text
git reset --hard
git clean -fd
git checkout -- .
git restore .
git stash
git rebase
git push --force
```

ولا تحذف ملفات أو تعديلات موجودة مسبقًا بحجة تنظيف المشروع.

إذا كان هناك سبب حقيقي لاستخدام أحد هذه الأوامر، توقف واشرح السبب للمستخدم وانتظر موافقته.

---

# 5. سياق المشروع وهويته الحالية (Project Context & Identity)

المشروع هو نسخة مستقلة قائمة بذاتها باسم:

**Atlas**

الهوية الأساسية للتطبيق متوفرة ومكتملة:

```text
اسم التطبيق (App Name):
Atlas

معرّف التطبيق (Application ID):
com.reda6dev.atlas
```

### قواعد الهوية البصرية المعمارية:

1. **مرحلة الهوية البصرية (Visual Identity Phase 2) مكتملة بالكامل:**
   تم توحيد الأيقونات التكيفية، شاشة البدء (Splash Screen)، الشعار بحجمه المضبوط في `LogoHeader.kt` (74dp)، وأنماط الرؤية في الأوضاع الفاتح، الداكن، وAMOLED. **لا تقم بإعادة تصميم الهوية البصرية دون طلب صريح من المستخدم.**

2. **لا تغيّر مساحة الأسماء/الحزمة (Kotlin namespace/package) الرئيسية تلقائيًا:**
   مساحة الأسماء (Namespace) الحالية للمشروع يجب أن تبقى:
   ```text
   eu.kanade.tachiyomi
   ```
   وجود هذا الاسم في الحزمة/مساحة الأسماء (Package/Namespace) ضروري للحفاظ على التوافق الكامل مع قاعدة البيانات الحالية والتنزيلات ومصادر الإضافات.
   **لا تقم باستبدال جماعي (Mass replacement) من `eu.kanade.tachiyomi` إلى `com.reda6dev.atlas`.**

3. **قبل إجراء أي تغيير في واجهة المستخدم (UI/UX):**
   يجب قراءة والرجوع إلى ملفات التوثيق التفصيلية في:
   `توثيق_Atlas/واجهة_المستخدم/`

# 6. قواعد خاصة بالم الموارد الرسمية والمعقدة (Resource Handling Rules)

1. **التعامل مع الموارد الرسومات المتجهة (Vector Drawables):**
   * عند حدوث انهيار (Crash) في مورد رسومي مثل `java.lang.IllegalArgumentException: Unknown command for: R` أثناء تحميل VectorDrawable، افحص المورد الفعلي وحجمه في Logcat/AAPT2 أولًا قبل التخمين.
   * السبب الشائع لهذا الخطأ هو تجاوز طول `pathData` حد 64KB المسموح به في مجمع النصوص (String Pool) الخاص بـ AAPT2، مما يتسبب في اقتطاع النص وكتابة أحرف تالفة عند معالجة الموارد في وقت التشغيل.
   * لا تعدّل ملفات الموارد المتجهة المعقدة أو الكبيرة يدويًا إذا كان بإمكانك إعادة تحويلها وتبسيطها باستخدام أدوات Android Studio الرسمية (Vector Asset Studio).

2. **الأجزاء التي يجب عدم تعديلها إلا بطلب صريح:**
   * `MdConstants.kt`
   * `tachiyomisy://mangadex-auth`
   * أي معرّف أو رابط عميق (Deep Link) داخلي مرتبط بالتوافق مع النظام القديم.

---

# 7. لا تعدّل ملفات البناء الناتجة (Build Artifacts)

أي ملفات داخل `app/build/` أو `*/build/` هي ملفات بناء مُولّدة (Build/Generated files) وليست مصدر المشروع. لا تعدّلها يدويًا، وابحث دائمًا عن ملف المصدر الأصلي.

---

# 8. نظام الإضافات (Extensions System)

يعتمد Atlas حاليًا على الأساس الحديث لـ TachiyomiSY (إصدار 1.13.2)، والذي يدعم نظام الإضافات الحديث بالكامل بما في ذلك: `index.pb` ومستودعات الإضافات الخاصة بـ Keiyoushi ومتجر الإضافات الحديث (Extension Store).

**لا تعُد إلى نظام `index.min.json` القديم ولا تعيد تصميم نظام الإضافات من الصفر دون سبب تقني واضح.**

---

# 9. مشاكل البناء التي تم حلها (Build Issues Resolved)

1. **محول العناصر المرن (FlexibleAdapter):** تم استبداله بـ `eu.davidea:flexible-adapter:5.1.0` في `gradle/libs.versions.toml` لحل خطأ JitPack 404. لا تغير هذا الإصدار عشوائيًا.
2. **SQLDelight والمنطقة المحلية (SQLDelight / Locale):** تمت معالجة مشكلة توليد الأرقام العربية-الهندية بإضافة `-Duser.language=en -Duser.country=US` إلى خيارات JVM في `gradle.properties`. لا تحذف هذه المعالجة.

---

# 10. قاعدة مهمة عند استخدام الذكاء الاصطناعي (AI)

إذا كنت تعمل كـ وكيل (Agent) وتستطيع رؤية المشروع كاملًا، **لا تطلب من المستخدم لصق الملفات التي تستطيع قراءتها بنفسك**.

ابحث داخل المشروع واستخدم أدوات البحث والبرمجة المتاحة لديك:

* البحث في الكود (Code Search)
* البحث عن الاستخدامات (Find Usages)
* الانتقال إلى التعريف (Find Declaration)
* فروقات Git (Git Diff)
* فحص شجرة المشروع (Find Files)

إذا كان هناك شيء غير واضح، افحص الكود أو ملفات توثيق الواجهة في `توثيق_Atlas/واجهة_المستخدم/` أولًا قبل سؤال المستخدم.

---

# 11. ممارسات التطوير والتحقق

بعد أي تعديل مهم:

1. افحص الفروقات: `git diff`
2. افحص الحالة: `git status --short`
3. أجرِ بناء للبرنامج (Build) واختبارًا مناسبًا على جهاز فعلي قبل الجزم بنجاح التعديل.
4. حدّث `AI_HANDOFF.md` وسجّل التغييرات في `ATLAS_CHANGELOG.md` بعد الانتهاء من المهمة.

---

# 12. لا توسّع نطاق المهمة (Do Not Expand Scope)

نفّذ **أقل تغيير ممكن يحقق المطلوب بأمان** دون إجراء استبدال جماعي للمكونات أو المسارات الحساسة.

---

# 13. البناء والاختبار (Build & Test)

بعد تعديل مؤثر على التطبيق:

1. البناء (Build).
2. إذا نجح، ثبّت التطبيق (Install).
3. اختبر الوظيفة التي تم تعديلها (Test) على جهاز فعلي.

نجاح `BUILD SUCCESSFUL` لا يعني بالضرورة أن التطبيق يعمل بشكل صحيح دون أخطاء في وقت التشغيل.
