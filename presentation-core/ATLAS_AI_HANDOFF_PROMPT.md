# AI HANDOFF — مشروع Atlas

أنت الآن تستلم مشروع Android قائم اسمه **Atlas**.
المشروع ليس مشروعًا جديدًا، ولا تبدأ بإعادة بنائه أو إعادة تصميمه من الصفر.

مهمتك أولًا هي **فهم الحالة الفعلية الحالية للمشروع**، ثم متابعة العمل من النقطة التي توقف عندها المشروع، مع المحافظة على التعديلات والقرارات الموجودة.

---

## 1. قاعدة أساسية جدًا

**لا تفترض أن هذه الرسالة تحتوي على أحدث حالة للمشروع.**

المصدر الحقيقي للحالة الحالية، بالترتيب:

1. ملفات المشروع الحالية.
2. Git والـ commit الحالي والـ branch الحالي.
3. `PROJECT_MAP.md`.
4. `AI_HANDOFF.md`.
5. هذه الرسالة.

إذا وجدت تعارضًا بين أي وصف هنا وبين الكود الفعلي أو Git، **لا تفترض أن الوصف صحيح**.

تحقق من الحالة الفعلية أولًا، وسجّل التعارض بدل إجراء تعديل مبني على افتراض.

---

# 2. قبل أي تعديل — ممنوع التعديل مباشرة

قبل إنشاء أو تعديل أو حذف أي ملف:

### اقرأ أولًا:

```text
PROJECT_MAP.md
AI_HANDOFF.md
```

إذا كان أحد الملفين غير موجود:

* لا تنشئه من نفسك أثناء تنفيذ مهمة أخرى.
* أخبر المستخدم أن الملف غير موجود.
* إذا كانت المهمة الحالية هي إنشاء/إعادة بناء الخريطة أو ملف التسليم، يمكن عندها إنشاؤه وفق التعليمات.

بعد ذلك افحص Git.

---

# 3. تحقق من Git

نفّذ أولًا أوامر قراءة فقط مثل:

```powershell
git status --short
git branch --show-current
git log -1 --oneline
git remote -v
```

ثم عند الحاجة:

```powershell
git --no-pager diff
```

ولفهم تاريخ التعديلات:

```powershell
git --no-pager log --oneline --decorate -20
```

إذا كانت هناك تعديلات غير محفوظة في Git:

```text
M
A
D
??
```

فلا تحذفها ولا تستبدلها ولا تعمل reset عليها من نفسك.

هذه التعديلات قد تكون جزءًا من عمل المستخدم.

---

# 4. ممنوع استخدام أوامر Git خطرة بدون موافقة صريحة

لا تستخدم من نفسك:

```text
git reset --hard
git clean -fd
git checkout -- .
git restore .
git stash
git rebase
git push --force
```

ولا تحذف ملفات أو تعديلات موجودة مسبقًا بحجة تنظيف المشروع.

إذا كان هناك سبب حقيقي لاستخدام أحد هذه الأوامر، توقف واشرح السبب للمستخدم وانتظر موافقته.

---

# 5. سياق المشروع

المشروع الأصلي مبني على:

**TachiyomiSY**

ويتم تطويره حاليًا كنسخة مستقلة باسم:

**Atlas**

المشروع هو تطبيق Android متعلق بقراءة وإدارة مصادر المانغا/الويب تون، ويحتوي على بنية متعددة الـ Modules وأنظمة متعددة للبيانات والمصادر والواجهة والإعدادات وغيرها.

المشروع يحتوي على أجزاء أصلية من TachiyomiSY بالإضافة إلى تعديلات Atlas الحالية والمستقبلية.

**لا تفترض أن كل شيء يجب إعادة تسميته من TachiyomiSY إلى Atlas.**

---

# 6. هوية Atlas

الهوية المطلوبة للتطبيق هي:

```text
App name:
Atlas

applicationId:
com.reda6dev.atlas
```

لكن هناك قاعدة مهمة:

### لا تغيّر الـ Kotlin namespace/package الرئيسي تلقائيًا.

الـ namespace الحالي للمشروع قد يكون:

```text
eu.kanade.tachiyomi
```

وجود هذا الاسم في package/namespace لا يعني أنه يجب تغييره.

**لا تعمل mass replacement من `eu.kanade.tachiyomi` إلى `com.reda6dev.atlas`.**

تغيير package/namespace موضوع منفصل يحتاج قرارًا صريحًا.

---

# 7. قواعد خاصة بالمشروع

هناك بعض الأجزاء التي يجب عدم تعديلها إلا إذا طلب المستخدم ذلك صراحة.

منها على سبيل المثال:

```text
MdConstants.kt
```

ولا تغيّر:

```text
tachiyomisy://mangadex-auth
```

فقط لأن المشروع أصبح اسمه Atlas.

أي قيمة أو identifier داخلي مرتبط بالتوافق مع النظام القديم يجب التعامل معه بحذر.

---

# 8. لا تعدّل ملفات Build الناتجة

أي ملفات داخل:

```text
app/build/
```

أو:

```text
*/build/
```

هي ملفات Build/generated وليست مصدر المشروع.

لا تعدّلها يدويًا.

ابحث دائمًا عن ملف المصدر الأصلي.

---

# 9. نظام Extensions

كان المشروع القديم يعاني من اختلاف بين نظام فهرس Extensions القديم ونظام Keiyoushi الحديث.

تم الانتقال إلى أساس أحدث من TachiyomiSY بحيث يدعم نظام Extensions الحديث، بما في ذلك:

```text
index.pb
```

ونظام Extension Store الحديث.

تم اختبار مصادر Extensions بعد بناء المشروع الجديد، والمصادر عملت بشكل صحيح.

لذلك:

**لا تعُد إلى نظام `index.min.json` القديم ولا تعيد تصميم نظام Extensions من الصفر دون سبب تقني واضح.**

إذا احتجت تعديل نظام Extensions:

1. افهم البنية الحالية أولًا.
2. اقرأ `PROJECT_MAP.md`.
3. تتبع الـ implementation الفعلي في الكود.
4. افحص Git diff.
5. اختبر Extension فعليًا بعد التعديل.

---

# 10. مشاكل Build التي تم حلها

المشروع واجه سابقًا مشكلتين مهمتين أثناء الانتقال إلى الأساس الجديد.

## FlexibleAdapter

كان هناك dependency قديم يشير إلى:

```text
com.github.arkon.FlexibleAdapter:flexible-adapter
```

مع commit من JitPack لم يعد متاحًا.

تم استخدام:

```text
eu.davidea:flexible-adapter
```

بالإصدار:

```text
5.1.0
```

إذا احتجت تعديل dependency، لا تغيّرها عشوائيًا. تحقق أولًا من الحالة الحالية في:

```text
gradle/libs.versions.toml
```

---

## SQLDelight / Locale

حدثت مشكلة لأن SQLDelight كان يولّد أسماء Kotlin تحتوي على أرقام عربية-هندية بسبب إعدادات لغة النظام.

تمت معالجة ذلك في:

```text
gradle.properties
```

باستخدام إعدادات JVM التي تجعل لغة Gradle الإنجليزية وبلدها US.

لذلك لا تحذف هذه المعالجة أو تستبدلها دون فهم سبب وجودها.

# 11. قاعدة مهمة عند استخدام AI

إذا كنت تعمل كـ Agent وتستطيع رؤية المشروع كاملًا، **لا تطلب من المستخدم لصق الملفات التي تستطيع قراءتها بنفسك**.

ابحث داخل المشروع.

استخدم:

```text
Search
Find Usages
Go to Definition
Git Diff
Gradle dependency inspection
Project tree
```

حسب الأدوات المتاحة لديك.

إذا كان هناك شيء غير واضح، افحص الكود أولًا قبل سؤال المستخدم.

---

# 12. استخدم AI المدمج في Android Studio بذكاء

إذا كنت تعمل داخل Android Studio وتملك وصولًا مباشرًا للمشروع، استفد من ذلك في:

* استكشاف بنية المشروع.
* البحث عن references.
* تتبع dependencies.
* فهم العلاقات بين Modules.
* البحث عن كل استخدام لاسم أو class أو resource.
* تحليل تأثير تغيير معين.
* إنشاء أو تحديث `PROJECT_MAP.md`.
* مراجعة أماكن التعديل المحتملة.

لكن لا تعتبر تقرير AI دليلًا كافيًا وحده.

بعد أي تعديل مهم:

```powershell
git diff
```

ثم:

```powershell
git status --short
```

وبعد ذلك Build/Test فعلي.

---

# 13. لا توسّع نطاق المهمة

إذا طلب المستخدم:

> تغيير اسم التطبيق

فلا تقم تلقائيًا بـ:

* إعادة تسمية جميع packages.
* تغيير namespace.
* إعادة هيكلة Modules.
* تغيير URLs.
* تغيير Deep Links.
* تغيير database schema.
* تغيير Extension system.
* تحديث dependencies غير المرتبطة بالمهمة.

نفّذ **أقل تغيير ممكن يحقق المطلوب**.

---

# 14. قبل تعديل أي ملف

حدد:

```text
1. ما الملف؟
2. لماذا هذا الملف؟
3. ما السطر/القيمة التي ستتغير؟
4. ما الذي لن يتغير؟
5. هل يوجد تأثير على أجزاء أخرى؟
```

إذا كانت المهمة بسيطة، لا تحتاج إلى كتابة تقرير طويل؛ يكفي فهم هذه النقاط داخليًا.

---

# 15. بعد تعديل الملفات

تحقق دائمًا من:

```powershell
git status --short
git --no-pager diff
```

وتأكد أن الـ diff يحتوي فقط على التغييرات المطلوبة.

إذا ظهرت تغييرات غير متوقعة:

**توقف ولا تنظفها تلقائيًا.**

اعرضها للمستخدم أولًا.

---

# 16. Build وTest

بعد تعديل مؤثر على التطبيق:

1. Build.
2. إذا نجح، ثبّت التطبيق.
3. اختبر الوظيفة التي تم تعديلها.
4. إذا كانت الوظيفة مرتبطة بـ Extensions أو الشبكة أو قاعدة البيانات، اختبر الجزء الفعلي وليس مجرد نجاح compilation.

نجاح:

```text
BUILD SUCCESSFUL
```

لا يعني بالضرورة أن التطبيق يعمل بشكل صحيح.

---

# 17. عند حدوث خطأ

لا تبدأ بتغييرات عشوائية.

اتبع:

```text
Error
↓
حدد الملف
↓
حدد السبب المباشر
↓
حدد dependency/configuration/logic المرتبط
↓
نفذ أصغر إصلاح
↓
Build
↓
Git diff
↓
Test
```

إذا لم تكن متأكدًا من السبب، قل بوضوح:

```text
السبب غير مؤكد بعد.
```

ثم اجمع الأدلة بدل التخمين.

# 18. PROJECT_MAP.md

`PROJECT_MAP.md` هو **خريطة تقنية للمشروع**.

يجب أن تعكس المشروع الحالي فعليًا، وليس وصفًا عامًا أو نسخة قديمة من TachiyomiSY.

يجب أن تساعد أي AI جديد على معرفة:

```text
Modules
Packages
UI
Data
Domain
Database
Networking
Extensions
Settings
DI
Localization
Gradle
Android configuration
Important entry points
Important files
Atlas-specific modifications
Sensitive/compatibility areas
Build/Test information
```

عند تحديث الخريطة:

**افحص شجرة المشروع والكود الفعلي أولًا.**

لا تعتمد على الذاكرة.

ولا تحوّل `PROJECT_MAP.md` إلى سجل محادثة طويل؛ وظيفته الأساسية هي **التوجيه التقني السريع**.

هذا الملف هو سجل حالة المشروع.

يجب أن يحتوي على أشياء مثل:

```text

Current commit
Base version
What has been completed
What has been tested
Known issues
Important decisions
Files intentionally changed
Files intentionally not changed
Current next task
```

---

# 20. لا تثق في الذاكرة القديمة

إذا وجدت معلومات قديمة تقول إن المشروع يستخدم نظامًا معينًا، بينما الكود الحالي يستخدم نظامًا آخر، فالكود الحالي هو المرجع.

مثال:

```text
Old implementation
        ≠
Current implementation
```

لا تحاول إعادة النظام القديم فقط لأن ملفًا قديمًا يذكره.

# 25. نقطة مهمة جدًا

**Atlas مشروع مستمر، وليس مجرد نسخة معاد تسميتها من TachiyomiSY.**

لكن في نفس الوقت يجب عدم تدمير التوافق والبنية الموجودة دون سبب.

أي تطوير جديد يجب أن يبدأ بفهم:

```text
ما الذي ورثناه؟
ما الذي تغير؟
ما الذي نريد تغييره؟
ما الذي يجب أن يبقى كما هو؟
```

# تعليمات الاستلام الآن

أنت الآن في مرحلة **استلام المشروع**.

لا تعدّل أي ملف.

ابدأ فقط بالآتي:

1. اقرأ `PROJECT_MAP.md`.
2. اقرأ `AI_HANDOFF.md`.
3. افحص Git branch وstatus وlatest commit.
4. افحص التغييرات غير المحفوظة.
5. قارن ما تقوله ملفات التوثيق مع الحالة الفعلية للمشروع.
6. لخّص لي فهمك الحالي للمشروع وحالته.
7. اذكر أي تعارض وجدته بين التوثيق والكود/Git.
8. اذكر الملفات أو الأجزاء التي تحتاج إلى فهم إضافي قبل تنفيذ المهمة التالية.

**لا تنفذ أي تعديل حتى يتم تأكيد نقطة الاستلام وفهم الحالة الحالية.**

بعد أن تؤكد أنك فهمت المشروع، سأعطيك المهمة التالية.
